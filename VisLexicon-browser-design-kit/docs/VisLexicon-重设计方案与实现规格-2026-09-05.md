# VisLexicon 重设计方案与实现规格

日期：2026-09-05　作者：本轮主设计师兼前端架构师　状态：可直接交付实现代理执行
证据基础：`research/00`–`04`、`context/01`–`07`、13 张 `current-ui-screenshots/`、`frontend/src/` 全部关键源码、`content-samples/approved-v3/` 12 个 JSON、`frontend/src/data/visual-atlas.json` 220 条（本文所有统计数字均为我在本机实测得出，命令与结果见第 11 节）

---

## 0. 结论先行

1. **产品的原子单位是「台」，不是卡片、不是词条。** 一台 = 把同一族东西并排摆在一屏上，配一组共同的对照轴。图鉴的九个活舞台已经是这个形态；策展现在缺的正是它。
2. **策展的一级组织单元改为「对照台」**：一个具体决定 + 3–6 个并排站点 + 一行共同轴（许可 / 拿走方式 / 核验时间）。卡片墙降级为兜底的「全部站点」，不再是首页主体。
3. **图鉴的一级组织单元仍是舞台，但舞台内部插入「分区」层**，并新增总览态（全标注）与对照态（行为矩阵）。一次只亮一个标签是当前最严重的结构错误（`research/03` §4.1）。
4. **顶栏三个频道：策展 / 图鉴 / 关于。** 工具与提交降级内嵌，`CodeExportModal` 与两张假端点卡整体删除。
5. **不做分类树、不做卡片墙、不做聊天框**之后，发现靠五个机制：场景对照台、位置索引、活体对照、切面 chips（带准入规则）、一个跨语料搜索框。
6. **详情必须有自己的路由** `#/site/<entryId>`。桌面浮窗、手机抽屉都只是这条路由的渲染形态。
7. **candidate 与 published 用两套正交标签表达**：建档深度（已入台 / 有证据 / 仅采集）× 术语地位（标准 / 通行 / 厂商 / 待定），加一条「人工复核于」，空着就是空着。
8. **Agent 端点 v1 只做三件**：`/r/registry.json`、`/r/{entryId}.json`、`/site/{entryId}.md`（采用 Google Labs DESIGN.md 规范并在 frontmatter 扩展出处三件套）。MCP、搜索 API、Skill 全部推迟。
9. **设计系统一次性收敛**：五组 token（色 / 字 / 距 / 角 / 影）+ 四个断点 + 一条 CI 门禁脚本，把 469 个硬编码 hex 收回去。基础字号从 14.5px 改为 16px，`--text-2` 从 3.22:1 提到 5.17:1。
10. **页面上任何数字必须由已加载数据算出**，字面量数字一律视为 bug；全站只保留一套口径，写在关于页。
11. **v2 保留 6 条、推翻 5 条**：推翻「工具/词典频道结论」「删除 primaryCategory 字段」「搜索缩成顶栏图标」「深读周更」「候选只做内部 backlog」。理由见第 10 节。
12. **本轮范围**：设计系统 token、导航壳、策展首页、全部站点、站点详情、图鉴舞台页。不做 URL 分析工作台、不做自然语言搜索、不做视频。

## 1. 产品定义、首屏契约、人与 Agent 的关系

### 1.1 一句话定义

> **VisLexicon 是一张把同类设计并排摆开的工作台：图鉴把同一族术语活体同屏摆出来让你调，策展把同一件事能用的站并排摆出来让你选，每一句判断都标着它的出处和核验时间。**

这句话有三个可被证伪的承诺（学 Siteinspire 的 “none of the featured sites are sponsored entries”，见 `research/01` §3.5）：并排、可调、可查。任何一个做不到，用户当场能拿反例打脸。这正是它有信息量的原因。

它同时回答了 Ben 的两条硬判断：

- **对 Refero Styles（判断 A）**：借它的分解顺序——隐喻 → 白话 → 数值 → Do/Don't → 导出（`research/01` §3.3 已用它的官方 MCP 数据模型证实这个顺序）；但**不借它的组织布局**。Refero 的洞在 `research/01` §3.3 结论里写得很清楚：整个数据模型没有一个字段能把某条判断连回具体页面证据。VisLexicon 的 `content-samples/approved-v3/*.json` 里 `pages[].selectionRationale`、`facts[].evidence`、`classification.reasons[].evidenceUrl` 三件套天生就是那个缺失字段。所以我们学的是节奏，占的是它的空位。
- **对 vocab.design（判断 B）**：`research/03` §1.2 实测它 1,124 词 / 4,087 别名 / 每条一个孤立小 demo / 无参数 / 无跨条对照。它的问题不是量，是**每一条都被单独关在自己的页面里**。VisLexicon 不做 A–Z 词表，不做一词一卡。九个舞台已经证明了另一条路：`data-display` 台把 Data table / Table / Grid / Treegrid / Listbox / Tree view 六种「看起来都是表格」的东西摆在同一屏（实测该台 19 个热区），这是 vocab.design 那种形态永远做不出来的信息。

### 1.2 首屏 3 秒内用户必须接收到什么

按优先级，三件事，多一件都不要：

1. **「这里的东西是成组摆出来的。」** 首屏必须**出现一个真实的台**，不是一句关于台的介绍。策展首页第一个内容模块就是第一张对照台，标题是一个决定（「要把组件装进项目，这 9 个站差在哪」），下面是并排的站与一行共同轴。
2. **「每一条都有人真的进去看过，而且写着什么时候看的。」** 承诺句 + 由数据算出的真实数字 + 最近一次核验日期，一行放完。
3. **「我可以从这里开始动。」** 首屏折叠线以上必须有一个可点的台入口。

明确不放在首屏的东西：分类 pill 行、五个下拉、搜索大输入框、候选池数字、任何 `+` 号结尾的数字、任何跑马灯。

三秒内**不需要**用户理解「策展」和「图鉴」的分工——那是第二屏的事。当前 `curation-1280x900.png` 的失败正在于：首屏 900px 里前 290px 是标题与筛选器，产品唯一无法被抄袭的那句「6 / 6 个已核验站点」被排成灰色小字贴在大标题右下角（`research/00` C.1）。这个层级必须倒过来。

### 1.3 人与 Agent：同一条记录的两种渲染，一先一后，不是两套产品

保留 v2 §3.2 的判断，并用 `research/02` §4 的实证加固：shadcn/ui 的 `/r/{name}.json` 与人页面是同一份数据的两种渲染，已被 292 个第三方注册表采用；Vercel Docs + skills.sh 同理。这个做法不需要发明。

具体关系定义如下，实现代理必须照此对待：

- **人得到的是判断，Agent 得到的是判断 + 它的出处标注。** 同一句「Uiverse 的内容可直接复制，但站上没有统一 SPDX 许可」，人在详情页看到的是这句话加一个可点的证据链接；Agent 在 `/r/uiverse.json` 里拿到的是 `facts[{field:"license", value, sourceUrl, evidence, confidence}]`。
- **Agent 通道永不收费、永不鉴权、永不限流**，静态文件生成。这是与 Refero（MCP 锁在 Pro 后、8,000 次/周期）和 Mobbin（MCP 需付费且工具表不公开）的定位分野，见 `research/01` §1、§2。
- **顺序不能反**：先有人工核验语料，再有端点。当前 6 条已发布 / 12 条样本的规模下，做搜索 API 是荒谬的（`research/02` §6.2）。
- **Agent 不写入。** 提交、投稿、纠错一律走人。写入型接口会直接污染「人工核验」这个唯一资产。

## 2. 顶层信息架构

### 2.1 频道：三个，加两个内嵌入口

| 频道 | hash | 是什么 | 为什么留 / 为什么砍 |
|---|---|---|---|
| **策展** | `#/`（默认） | 对照台目录 + 全部站点 + 站点详情 | 它是首页。首页不需要再叫一次自己的名字，但顶栏需要一个回家的词 |
| **图鉴** | `#/atlas` | 四入口索引 + 九个活舞台 | 全仓唯一别人一周复制不了的资产（`research/00` F.2 质疑一） |
| **关于** | `#/about` | 方法论、数字口径、核验日志、Agent 端点说明、我们删掉了什么 | v2 §3.3 建议新增，成立。它是承诺句唯一可被核验的落点 |
| ~~工具~~ | — | 删除频道 | 两个工具中 Spec 提取器与 ΔE 描述器有价值（`research/00` E.2 保留清单），但它们是**编辑部工具**不是用户频道；两张协议卡指向不存在的端点（`Tools.jsx:443–465`，`public/` 下无 `lexicon/` 与 `llms.txt`）必须删 |
| ~~提交~~ | — | 降为页脚查重框 | `Submit.jsx` 的文案纪律很好（每个状态都写「尚未发送」），保留这份纪律，去掉频道位 |

工具的去处（具体到模块）：

- ΔE 差异描述器 → **关于页 §「我们怎么核验一张截图」** 的一个可展开演示，输入源默认给站内已有的 `public/shots/` 图，不要求用户自带截图（解决 `research/00` B.5 指出的「站内有 36 张核验图却没有一条路径用它们」）。
- k-means 取色 Spec 提取器 → **不上线**。它输出的 `unitSystem: "8pt-grid"`、`colorSpace: "OKLCH / sRGB"` 是硬编码常量不是测量结果（`research/04` 结论 9），先修数据纪律再谈上线。

提交的去处：页脚一个 URL 框，`#/about#submit` 锚点承载完整说明。当前查重预检 `fetch('/data/curation/manifest.json')` 恒 404（`Submit.jsx:61–96`），所以 v1 **不做五态查重**，只做两件诚实的事：(1) 本地比对已发布索引，命中就直接跳那条站点详情；(2) 未命中就说「本站当前没有接收后端，你可以复制这段 JSON 发给我们」。不给假的「已在候选处理中」。

### 2.2 互相导流：逐个链接点

这是 `research/00` B.2/B.3 点名的零导流问题的修法。下表每一行都是一个必须实现的具体元素，实现代理按此验收。

| # | 起点（模块 · 元素） | 终点 | 数据来源 |
|---|---|---|---|
| L1 | 策展首页 · 对照台的每个站点格 · 站名 | `#/site/<entryId>` | `benches.js` 的 `entryIds[]` |
| L2 | 策展首页 · 对照台标题行右侧「这一族的术语在图鉴」 | `#/atlas/<stageId>` | `benches.js` 的 `atlasStageId` |
| L3 | 站点详情 · 第 4 段「这个站示范了哪些术语」的每个 chip | `#/atlas/<stageId>/<termId>` | 新增编辑字段 `curation.atlasTerms[]`；域名反查作兜底 |
| L4 | 站点详情 · 三张证据图每张的「看原页 ↗」 | `pages[].sourceUrl`（新标签外跳） | `approved-v3` 的 `pages[].sourceUrl`，当前投影已丢，需补 |
| L5 | 站点详情 · 每条事实右侧的来源角标 | `facts[].sourceUrl`（新标签外跳） | `facts[].sourceUrl` |
| L6 | 图鉴 · 术语面板「真实网站里长这样」的每个条目 | `#/site/<entryId>` | `lib/atlas-source-link.js` 域名反查 + L3 的人工标注反向索引 |
| L7 | 图鉴 · 舞台页页脚「这一族在策展里的对照台」 | `#/#bench-<benchId>` | `benches.js` 的 `atlasStageId` 反查 |
| L8 | 全部站点 · 空结果态「没有匹配」 | 页脚查重框（聚焦） | — |
| L9 | 关于页 · 数字口径表的每个数字 | 对应列表页（如「已发布站点 12」→ `#/sites`） | `lib/counts.js` |
| L10 | 全站搜索结果 · 两个分组标题 | `#/sites?q=` 与 `#/atlas?q=` | 见 §3.6 |

**L3 是本轮最高杠杆的一条**，也是全行业没人做的那件事（`research/03` §5：术语 ↔ 野生真实网站的互链，四种现有做法都只走了半步）。它的成本是编辑在核验一个站时顺手勾 2–3 个术语（v2 §7 的判断成立）。

**必须说明域名反查为什么不够。** 我实测了 `lib/atlas-source-link.js` 的机制：12 个已复核站点里，只有 `chakra-ui.com` 一个域名在 220 条图鉴样本的 `sourceEvidence[].url` 里出现过，命中 33 条术语；其余 11 个站命中 0 条。也就是说这条自动链路的覆盖率是 1/12。它可以留作兜底，但**不能作为主机制**——主机制必须是人工标注字段。

## 3. 发现方式：不做分类树、不做卡片墙、不做聊天框之后

`research/01` §3.2 给出的裁决很硬：整个赛道没有一家真正做到「不靠分类树也能逛」，能接近的都用同一招——**把可轮换的编辑策划入口放在固定 schema 分类的位置上**。同一节也补了一条 v2 没说的话：编辑策划的入口没有覆盖保证，所以必须配一个兜底出口。

下面五个机制按这个原则设计，每个都在真实样本上验证过可落地。

### 3.1 机制一 · 场景对照台（服务「我知道自己在做什么」）

**定义。** 一台 = `{ 一个决定句 + 3–6 个 entryId + 3 条共同轴 + 一句为什么是这几个 }`。它不是标签，不是分类，是编辑写的一份并排比较。

**为什么它能替代卡片墙。** 卡片墙让用户在一片同构卡片里自己找差别；对照台直接把差别摆出来。Ben 对 Refero Styles 的批评（「只能漫无目的地在一片设计里自己找」）在策展侧的解法就是这个。

**用真实样本验证它现在就能做出来。** 12 个 v3 条目的主类分布是：`ui-implementation` 9、`case-inspiration-collections` 1、`research-quality-tools` 1、`reference-standards` 1。也就是说样本天然只支持 **两台**：

**台 1 · 「要把组件装进自己的项目，这 9 个站差在哪」**
成员：shadcn/ui、21st.dev、Uiverse、Magic UI、Coss UI、Hover.dev、Chakra UI、Ant Design、Shadcn Studio Blocks
共同轴（三条，全部来自 v3 真实字段）：
- **许可**（`facets.licenses`）：样本实测 MIT 6 / custom 4 / Apache-2.0 1 / unknown 1
- **怎么拿走**（`facets.actions` 交 `{copy, install, download, purchase}`）：copy 9 / install 7 / purchase 3 / download 1
- **核验于**（`official.checkedAt`）

**台 2 · 「先把话说对：三个可以引用的参考站」**
成员：Laws of UX、A11Y Project、ecomm.design
共同轴：它教什么（`facets.deliverables`：glossary / standard / case-screenshot）· 能不能引用（`facets.licenses`：样本里两条 custom、一条 unknown）· 核验于

**只做两台是正确的，不是不足。** 一个 12 条语料的库如果首页挂 6 台，每台就只有 2 个成员，这就是 `research/01` §3.2 说的 Saaspo 病（Corporate 只命中 2 个的死值）。台的数量必须由语料算出：**每台成员数下限 3，台数 = floor(已发布条目数 / 4)，上限 6。** 12 条 → 3 台，实际做 2 台（第 3 台成员不足 3 就不出现）。这条规则写进 `data/benches.js` 的校验函数，构建期抛错。

**台的生命周期。** 每台带 `createdAt`，关于页列出全部台及其上架日期，复审时先看最老的（`research/01` §B3 的建议：任务词表必须带上架日期）。台不是 schema，可以下架。

### 3.2 机制二 · 位置索引（服务「我知道它在哪，但不知道它叫什么」）

`research/03` §3 机制八实测：**全行业没有一家提供位置检索。** 而 `context/04` 的舞台模型开头就写着「位置本身就是索引」——VisLexicon 现在只把位置做成了浏览方式，没做成检索方式：用户必须先选对舞台，再逐个悬停 21 个热区，才能撞上他要的那个。

**落地形态。** 图鉴索引页（`#/atlas`）第二个入口是一张抽象版面图，七个可点区域，每个区域列出「哪些台的哪些术语长在这里」：

| 区域 | 现有舞台与热区（实测） |
|---|---|
| 顶栏 / 服务级 | navigation（nav.service / nav.lang / nav.menubar / nav.breadcrumb） |
| 侧栏 / 目录 | navigation（nav.rail 系）、agent-composer（会话列表侧栏） |
| 主内容区 · 表格 | data-display（19 个热区） |
| 主内容区 · 表单 | form-anatomy（21 个热区） |
| 浮层 / 遮罩 | overlay-layers（13 个变体 + 1 热区） |
| 底部输入区 | agent-composer（composer 一族） |
| 加载与空态 | state-loading（3 变体 + 6 热区） |

这张图的每个区域必须显示它当前覆盖多少条术语（由 `stage-index.js` 算出），**为 0 的区域显示为「这一区还没有台」，不隐藏**——这是 Growth.design 把 “Coming Soon” 与成品同列的做法（`research/03` §1.15），比藏起来诚实。

### 3.3 机制三 · 活体歧义对照（服务「两个词我分不清」）

`research/03` §6.4 第六条判定这是 VisLexicon 唯一能碾压全部竞品的功能：所有人的歧义对照都是静态图配文字，只有活舞台能把两个易混淆的东西同屏、活体、同参数摆在一起当场按一按。

**本轮的落地方式是舞台页的第三个视图，不是新路由。** 在 manifest 里新增 `compareSets[]`，每组 = `{ id, titleZh, termIds[2..4], axes[] }`，axes 用 namethatui.org 的五轴（焦点 / 键盘 / 消解方式 / 模态性 / 持久性，`research/03` §1.4）。

**现有数据立刻支持两组，零采集成本：**
- `form-anatomy` 台：Checkbox / Checkboxes / Radio button / Radio group / Switch —— 五条已经在同一屏上（manifest 实测 21 个热区里就有这五条），把它们的行为差别做成一张矩阵即可。manifest 里已经写好了判据原文：「单选组内部只有一个 tab 停靠点，方向键在组内移动。这是它和复选框组最大的行为差别。」
- `overlay-layers` 台：Tooltip / Popover / Dialog / Dialog (Modal) —— 13 个变体里已有这四条，manifest 的批注已写「模态：遮罩 + 焦点陷阱 + 底页惰性。用户不回应就走不了。」

**编辑纪律：** 判据是「会改变实现的那条需求」，不是「长得像不像」（`research/03` §1.4 的方法论原话）。任何一条写不出这种判据的对照组不得上线。

### 3.4 机制四 · 切面 chips（服务「我要精确收口」）

切面只在**已经有结果集之后**出现，首页零筛选器。这一条保留 v2 §4.5。但 v2 没给准入规则，我用真实样本补上，并且规则本身可执行：

**准入规则（写进 `lib/facet-chips.js`，构建期与运行期都跑）：**
1. 命中数 `< 2` 的值不显示（Saaspo 的死值病，`research/01` §3.2）。
2. 命中率 `> 60%` 的值不显示（Siteinspire 的 Typographic 占 88% 病，同上）。
3. 一个轴上剩余可显示的值 `< 2` 时，整条轴不显示。

**用 12 个样本实测这条规则的效果**（这是这套规则值不值得做的唯一证据）：

| 轴 | 实测分布 | 规则裁决 |
|---|---|---|
| `media` | ui 12/12 | **整轴不显示**（100% 命中） |
| `platforms` | web 12/12，cli 5，mcp 2，figma 1 | web 剔除，剩 cli/mcp 可显示 |
| `audiences` | designer 12、developer 12、educator 2、brand-team 1、researcher 1 | 前两个剔除，剩 educator 一个 → **整轴不显示** |
| `languages` | en 12/12、zh-hans 1 | **整轴不显示** |
| `actions` | browse 12、preview 10、copy 9、install 7、search 6、learn 5、purchase 3、submit 3 | browse/preview 剔除（>60%），剩 copy/install/search/learn/purchase/submit |
| `licenses` | MIT 6、custom 4、Apache-2.0 1、unknown 1 | **全部显示**（MIT 恰好 50%）——最有区分度的一轴 |
| `access` | free 8、open-source 7、freemium 4、source-available 3、closed-source 2、paid 1、login-required 1 | free 剔除（66.7%），其余显示 |
| `deliverables` | component 9、block 6、code-library 3、primitive 3、template 3、standard 3、case-screenshot 2、report 2、prompt 2、glossary 2、full-page 1 | component 剔除（75%），其余显示 |
| `contentOrganization` | component-registry 9、searchable-directory 8、standards-documentation 6、case-gallery 2、editorial-feed 2、community-feed 2、marketplace 1、course 1 | 前两个剔除，其余显示 |

结论：**12 条语料下，规则自动把 12 个轴收敛成 5 个有用的轴（licenses / access / deliverables / actions / contentOrganization），并且自动干掉了 4 个 100% 命中的废轴。** 这比手写一份「首页放哪几个筛选器」的清单可靠得多，而且语料长大时会自己调整。

**同时这条规则解决了 `research/00` D.2 点名的「12 个正交轴被压平成一个 tags 袋子」**：投影层必须保留 12 个轴的结构（`site-index.json` 的 `facets` 对象），前台按轴渲染，绝不再合并成 `tags[]`。

### 3.5 机制五 · 主分类退出前台（但字段留在后台）

`research/00` D.3 已经查清：`primaryCategory` 在前台有 0 处依赖，删掉它用户一秒都感觉不到，而删它会连带废掉 `curation-taxonomy.js:711–715` 唯一一条实质准入规则。加上我实测的分布——12 条里 9 条是 `ui-implementation`（75%）——按 §3.4 的规则，主分类本来就是一条 100% 该被剔除的轴。

**决定：字段留在数据与端点里，前台一处不渲染。** 不做分类下拉，不做分类导航，不做分类分组。`SiteCatalog.jsx:226–276` 的五个下拉全部删除。

### 3.6 一个跨语料搜索框（推翻 v2 §5）

v2 说「搜索框放顶栏、不做 hero」，理由是大输入框是 AI 产品模板动作。前半句对，后半句错在它没看代码：当前**顶栏根本没有搜索框**，而 `IndexView`（第 69–75）、`SiteCatalog`（第 217–223）、`Atlas` 左抽屉（第 369–372）、`Palette`（第 26–40）各有一个互不相通的搜索框，共四个（`research/00` F.2 质疑四）。

**决定：全站一个搜索框，放顶栏，跨两个语料，结果分两组。** 这是把四个频道重新变回一个产品的唯一现成机制。

- 输入 `skeleton` → 分组一「图鉴里的」：Skeleton（状态与加载台 · 部件）、Shimmer；分组二「站点库里的」：命中描述与切面的条目。
- 输入 `MIT` → 分组二命中 6 个站（实测 `licenses` 分布）。
- 输入 `复选框` → 命中 `form-anatomy` 台的 Checkbox / Checkboxes（`termZhFix` 与 `aliases` 都进索引）。
- 索引字段（`lib/search-index.js`）：术语侧 `termEn / termZh / claim.termZhFix / aliases[] / definitionZh` 前 60 字；站点侧 `name / domain / descriptionZh / facets 全部值 / subcategory`。
- **纯前端，无网络，无 LLM。** 220 条术语 + 12 条站点的索引在客户端构建，耗时可忽略。

**明确不做的**：「你现在想做什么？」式提问框、自然语言理解、截图反查。后两者是第三阶段（`research/03` §3 机制九指出截图反查是全行业空白，值得做，但不是现在）。

### 3.7 兜底出口：全部站点

编辑策划的入口没有覆盖保证（`research/01` §3.2 结尾的补充）。所以必须有一格保证「每个条目都能被够到」：`#/sites` 全部站点，单一列表 + §3.4 的切面 chips + 排序（最近核验 / 名称）。**这一格不能砍。**

## 4. 策展：首页、全部站点、站点详情

### 4.1 三种卡片模板：采纳，但改判定依据

v2 §6.1 提出三种模板（A 资源型 / B 作品型 / C 知识工具型），方向对。但它按「站点机制 + 媒体形态」选择，而 v3 数据里没有「站点机制」这个字段。我改用一个**可从真实字段计算**的判定函数，实现代理照抄即可：

```js
// lib/site-card-template.js
export function templateFor(entry) {
  const org = new Set(entry.facets?.contentOrganization ?? [])
  const del = new Set(entry.facets?.deliverables ?? [])
  // C：知识 / 工具型 —— 拿走的是理解，不是文件
  if (org.has('standards-documentation') || del.has('glossary') || del.has('standard')) return 'C'
  // B：作品型 —— 站点自身就是被研究的样本
  if (entry.classification.primaryCategory === 'single-site-showcase') return 'B'
  // A：资源型 —— 有可复制/可安装的交付物（默认）
  return 'A'
}
```

**用 12 个样本跑一遍的结果**：Laws of UX、A11Y Project → C（`deliverables` 含 glossary/standard）；ecomm.design → A（case-gallery + template，走资源型）；其余 9 个 `ui-implementation` → A。**样本里一个 B 都没有**，因为 12 条里没有 `single-site-showcase`。

这是重要结论：**本轮实现 A 与 C 两个模板即可，B 模板不实现。** 造一个用不上的模板就是造 `research/00` 批评的那种「用结构性的壳替代还没做完的编辑工作」。B 模板的规格写进本文档备查（单幅大图 + 名称 + 一句气质判断 + 「仅参考」微标），等第一个 `single-site-showcase` 条目进库时再实现。

三种模板同宽、两档高度，卡片墙节奏不破。

### 4.2 卡片上最少放什么（1.5 秒判断）

v2 §6.2 定了四项（媒体 + 名称 + 一句「拿走什么」 + 权利/价格微标）。`research/01` §A1 提出应扩成五项，加上**核验时间**。我采纳，并加一条数据纪律：

| 卡上元素 | 字段来源（v3 JSON 路径） | 缺失时 |
|---|---|---|
| 主图 | `pages[0].shot.src`（role=identity） | 显示域名首字母块（复用 `SiteDetailModal` 的 `DomainMark`） |
| 名称 | `editorial.name` | 不可缺，构建期抛错 |
| **一句「拿走什么」** | **新增字段 `editorial.takeawayZh`（≤ 28 字）** | 显示 `descriptionZh` 前 28 字并加下划虚线标记「未写」 |
| 权利微标 | `facts[field=license].value`，映射为 `MIT` / `Apache-2.0` / `自定条款` / `未知` | `未知`（v3 §4.1 规定找不到必须是 unknown，不得猜）——**空值本身是差异化** |
| 核验于 | `official.checkedAt` → `YYYY-MM-DD` | 不可缺，构建期抛错 |

**`takeawayZh` 是本轮唯一需要新增的内容字段。** 理由在 `research/00` D.2 第 2 条已经写死：v3 的 `descriptionZh` 被要求同时干三件事（定位 + 规模 + 价格 + 许可 + 限制），实测 `entry-shadcn-studio-blocks.json` 那句是 200 字长句，卡片上只能截断成半句。「一句拿走什么」这个字段在数据模型里不存在，所以前台造不出来。**12 条 × 28 字 = 一次不到一小时的编辑工作**，这是全案性价比最高的一处内容投入。

不上卡的：技术栈 pill 行（只对 A 型有意义，且当前是紫色靛蓝那族未进 token 的颜色）、主题 pill 跑马灯（`research/00` C.1 实测两端都在切字：「ph Matrix」「aint buttons」）、分类标签、任何计数徽章。

### 5.1 图鉴的默认入口不是舞台

### 5.2 舞台页的三态结构

这是本轮图鉴最重要的改动。依据是 `research/03` §4.1 的实测：全行业解剖图的标注密度是 3–7 个（namethatui.com 3、uianatomy.dev 6、Carbon 6），而 VisLexicon 单台挂 14–39 个热区且一次只亮一个标签——是行业上限的 3–6 倍，同时把静态解剖图唯一的价值（一眼看到全部命名）丢了。

我实测了九台的真实密度：

| 舞台 | 认领总数 | variant | hotspot | param | knobs |
|---|---|---|---|---|---|
| pointer-gestures 指针与手势 | 39 | 9 | 6 | **24** | 2 |
| agent-composer Agent 界面 | 26 | 3 | 22 | 1 | 5 |
| form-anatomy 表单解剖 | 21 | 0 | 21 | 0 | 3 |
| data-display 数据展示 | 19 | 0 | 19 | 0 | 3 |
| surface-transition 过渡形变 | 16 | 16 | 0 | 0 | 3 |
| text-reveal 文字与排版工坊 | 15 | 13 | 1 | 1 | 5 |
| navigation 导航 | 14 | 1 | 13 | 0 | 3 |
| overlay-layers 浮层 | 14 | 13 | 1 | 0 | 3 |
| state-loading 状态与加载 | 9 | 3 | 6 | 0 | 3 |
| **合计** | **173**（170 条唯一术语，3 条跨台复用） | 58 | 89 | 26 | 30 |

**三态定义：**

**态一 · 总览态（新增，且是舞台的默认态）。** 全部热区同时显示编号角标，右侧一列图例（编号 → 正名 → 中文名）。点图例高亮部件，点部件滚到图例。这是 Carbon 与 M3 的解剖图范式，只是我们的版本是活的。用户第一眼看到的是「这屏一共 21 个名字」，而不是「这屏什么都没有，你自己去扫」。

**态二 · 分区态（新增一层）。** 按**空间**切分，每区 3–7 个，落回行业密度区间。这一层解决 `research/03` §6.4 第三条点名的问题：当前左栏按 `变体 / 部件 / 参数` 分组是按**数据模型**分，用户不会想「我要找一个 hotspot」，他会想「我要找输入框旁边那个东西」。

各台的分区方案（写进 manifest 的 `zones[]`，实现代理照抄）：

| 舞台 | 分区（每区 3–7 个热区） |
|---|---|
| form-anatomy | 文本录入（text / password / number / date / datepicker / search）· 选择控件（select / dropdown / combobox）· 多选与单选（checkbox / checkboxes / radio / radio-group / switch）· 范围与长文（slider / slider-multi / textarea / charcount）· 提交与反馈（fieldset / upload / error） |
| agent-composer | 会话侧栏 · 会话标题栏 · 消息与推理块 · 输入区 composer · 产物画布 |
| data-display | 表格类（data table / table / grid / treegrid）· 列表类（list / listbox）· 树类（tree view / file tree）· 标记与图形（tag / chart / heatmap / code block） |
| navigation | 服务层（skip / service / lang）· 应用层（menubar / menu button / menu / toolbar）· 页面层（breadcrumb / tabs / back / anchor）· 翻页与回顶（pagination / scroll button） |
| state-loading | 占位（skeleton / shimmer）· 指示（loader / job progress）· 结果态（empty / error） |
| overlay-layers | 变体台无空间分区，改按**行为**分区：非模态提示（tooltip / popover 系）· 模态对话（dialog / modal / alert dialog）· 通知与状态（notification / alert / status bar） |
| text-reveal / surface-transition / pointer-gestures | 变体台，分区 = 变体分组（见 §5.4） |

**态三 · 单词态（现状）。** 聚焦一条，右栏展开，其余热区降为浅描边不消失。

**态四 · 对照态（新增，§3.3）。** 舞台内的 `compareSets`，一张行为矩阵 + 同屏两到四个活体。

层级路径从 `领域 → 舞台 → 术语` 变成 `领域 → 舞台 → 分区 → 术语`，每层分支数落回 3–7。

**与现状的六处结构差别（每处都对应一条实测证据）：**

1. **参数从底部横条改为右侧贴边面板，每控件一行。** 依据：`research/03` §4.3 实测横条容量上限 3–4；而 `pointer-gestures` 台有 **24 个 param + 2 个 knob = 26 个控件**，截图 `atlas-pointer-gestures-1440.png` 里它们排成 3 列并延伸到折叠线以下，多个初始值为 0 使滑块钮全堆在最左端。侧面板可纵向延伸，且天然容纳 enum 下拉与 boolean 开关（文档说支持三类，截图里三个舞台全是 range）。
2. **param 与 knob 在视觉上分开。** `context/04` 明确区分：`param` 是有正名的术语挂点，`knobs` 是「没有对应术语的纯微调旋钮……不伪造术语 id」。这个区分在数据层做得很干净，在界面上一点痕迹都没有。新方案：术语参数分组带正名标记且可点进右栏，微调分组明确标「无正名」且不可路由。**既然项目把「不伪造术语」当原则，界面就必须让这条原则可见。**
3. **补预设档位。** MDN 的 Try it 用预设值点选（`linear` / `ease-in` / `steps(6, end)`）而不是空白滑块，让人一眼看出取值区间与差异（`research/03` §1.9）。每个舞台给 3 个有名字的档位。
4. **左栏改按分区组织，搜索上提到栏首。** 当前左栏同时承载 8 领域树 + 搜索框 + 术语列表三种东西，搜索框夹在中间把列表切成两半——`atlas-state-loading-1440.png`、`atlas-data-display-1440.png`、`atlas-pointer-gestures-1440.png`、`atlas-surface-transition-1440.png` 四张截图四次复现「列表被搜索框切掉半行」。领域树移到 `#/atlas` 索引页，舞台页左栏只放本台分区与术语。
5. **右栏按 Laws of UX 的节奏重排。** 当前 13 个区块塞在一条约 300px 宽的柱子里，最有价值的原创批注排第 7 位，最硬的可信证据（带许可证与日期的来源卡）排第 11 位（`research/03` §4.4 实测）。新顺序：正名/中文名 + 两套状态标签 → **编辑批注** → 一句定义 → 别名与易混淆 → 折叠的「证据与去处」。

### 5.5 candidate vs published：两套正交标签

硬约束第 2 条禁止 `candidate` 伪装成已审核内容。实测：`visual-atlas.json` 的 `stats.byStatus` 是 `{candidate: 219, published: 1}`，`translationQuality` 是 `machine` × 220/220，而 `Atlas.jsx` 全文没有一处读取 `entry.status`。

而且这不是抽象风险。我在 220 条样本里实测到的原始记录质量：

- `all`（MDN CSS 属性）：中文定义是「CSSshorthand 属性全部重置元素属性, unicode- bidi, 方向和 CSS Custom 属性除外」——机翻，且它根本不是一个视觉现象。
- `background`：中文名被译成**「背景情况」**。
- `backface-visibility`、`backdrop-filter`：MDN CSS 属性直接进图鉴。
- 唯一一条 `published` 是 `Drag to reorder`，来自 animations.dev，`translationQuality` 仍是 `machine`。

**决定：两套正交标签，不合并成一个字段（这也是硬约束第 3 条的直接应用）。**

| 标签组 | 值 | 判定依据 | 数据来源 |
|---|---|---|---|
| **建档深度**（我们做到哪一步） | `已入台` / `有证据` / `仅采集` | 有活体演示 / 有定义与来源但无演示 / 只有来源里的一行 | `stage-index.js` 的认领关系 + `entry.status` |
| **术语地位**（这个词在行业里算什么） | `标准术语` / `行业通行` / `厂商用语` / `待定` | APG/WHATWG/MDN/HIG 有正式定义 / ≥2 个主流设计系统在用 / 单一厂商 / 其余 | **新增字段** `termStanding`，由 `sourceEvidence[].sourceId` 的数量与身份自动初判，人工可覆盖 |

`termStanding` 的自动初判规则（写进 `lib/atlas-status.js`，可完全从现有数据算出）：

```
sourceIds 含 wai-aria-apg / open-ui / mdn-css / govuk-design-system → 标准术语
唯一 sourceIds 数 ≥ 2                                              → 行业通行
唯一 sourceIds 数 = 1                                              → 厂商用语
无 sourceEvidence                                                   → 待定
```

实测这条规则在样本上有效：`Combobox` 有 ark-ui + chakra-ui 两个来源 → 行业通行；`Tabs` 有 ark-ui + bulma + … → 行业通行；`backdrop-filter` 只有 mdn-css → 标准术语；`Account connection`（Shopify Polaris 的业务组件）只有一个来源 → 厂商用语，这恰好把它和 `Tabs` 区分开了——而当前界面上它们权重完全一致。

**第三个必须可见的诚实标记：译名欠账。** 当前 `Atlas.jsx:479` 在 `translationQuality === 'machine' && !claim.zhFixed` 时显示「机器译名 · 待校」，这是全站最诚实的一个微设计（`research/03` §6.3 第 4 条也点名表扬）。**保留并强化**：未订正的显示「中文名为机器翻译，未经人工校对」，已订正的显示「语料原译「X」已在台上订正」（现状已有）。`machineNameDebt()` 的数字上关于页。

**图鉴索引页必须有一句同等分量的话**（学 A11Y Project 的 “targets many, but not all level A and AA concerns”）：

> 图鉴不是一份完整词表，也不打算是。样本库里 220 条中有 219 条只是带来源的采集记录；真正被摆上台、能调、有人校过名字的是 170 条。我们把 170 当成资产，不把 220 当成规模。

### 10.2 推翻（5 条）

**推翻一 · §3.3「工具降级、词典保留 62 个真词条撑得起一个频道」——整体重做。**
理由：v2 自己声明只读了两份文档、没读代码、没看截图，因此**完全不知道 9 个可交互舞台的存在**。代码事实是：9 个手写舞台、173 条认领（170 条唯一术语）、三种挂载槽位、跨台互引、构建期契约校验，据 `context/04` 有 435 项测试与 57 项真实浏览器断言。这是整个仓库里唯一别人无法用一周复制的东西。v2 把它当成「62 个词条」来处置，等于建议把最有价值的资产降级。**任何以 §3.3 为基础的频道结论都必须重做**——本文的三频道结论是从代码事实重新推的，不是从 v2 继承的。

**推翻二 · §4.1「数据模型里删掉主分类字段本身」——找错了病灶。**
`primaryCategory` 在前台有 0 处依赖，只活在三个**当前不可达**的后台校验模块里；删掉它用户一秒都感觉不到，却会一并废掉 `curation-taxonomy.js:711–715` 里唯一一条实质性的准入规则（单站类必须有三页证据 + 人工理由 + 设计相关确认）。真正制造「数据库味」的是三样具体东西：五个下拉、被压平成一个袋子的 `tags`、浮窗里的字段 `<dl>` 罗列。**正确的手术对象是 `entry.tags` 那一次压平，不是 `primaryCategory` 这个字段。** 本文的处置：字段留在后台与端点，前台一处不渲染（§3.5）。

**推翻三 · §5「搜索框缩成顶栏一个图标，不做 hero」——后半句对，前半句错。**
「不做大输入框 hero」正确并采纳。但「缩成一个图标」建立在「已经有一个统一搜索」的错误假设上：代码里顶栏**根本没有搜索框**，而四个互不相通的搜索框散落在 IndexView、SiteCatalog、Atlas 左抽屉、Palette 里。VisLexicon 有站点与术语两个语料，**跨语料检索恰恰是把频道重新变回一个产品的唯一现成机制**（搜 `skeleton` 应当同时得到骨架屏舞台与相关站点）。本文的处置：顶栏一个真搜索框，结果分两组，纯前端（§3.6）。

**推翻四 · §8「深读每周一篇带证据回链的编辑产品」——本阶段是净负债。**
v2 自己在 §2.2 算过编辑工时的账（2,000–3,000 小时），又在 §8 叠加一项周更承诺。在只有 12 条核验语料、`takeawayZh` 这个基础字段都还没写的阶段引入周更栏目，是把编辑成本叠加到已经做不完的核验成本上。**第二阶段之前不做任何「周更」承诺。** 替代动作：关于页的月度核验日志（学 Nicelydone，`research/01` §A6），成本接近零，且十年后它会变成这个产品最有价值的资产。

**推翻五 · §7「419 条图鉴候选只做内部 backlog，最多以『研究中』名单出现」——反了。**
代码事实：候选**就是**图鉴主体（样本里 219/220 是 candidate，生产里 1,926/1,932）。把主体做成内部 backlog 等于把图鉴变成一个 6 条记录的产品。正确做法不是藏，是**诚实分级**：两套正交标签 + 人工复核日期 + 一段承认覆盖边界的自述（§5.5）。这也是 `research/03` §6.3 从 Growth.design（"Coming Soon" 与成品同列同框）、namethatui.com（术语地位四分法）、uianatomy.dev（逐源 fetch 日期 + Last reviewed）三家实测得出的结论：**规模小、标注诚实，反而是可信度证据**——namethatui.org 就是拿「44 条已复核、零 AI 置信度分数」当首屏卖点的。

### 10.3 v2 之外、本轮新增的三条判断

1. **对照台是策展的一级组织单元**（Ben 判断 A 的直接落地）。v2 提的「任务货架」方向对，但货架仍是「一堆卡片按任务分组」；对照台多了一样东西——**共同轴**，它才是让人不必自己去找差别的那个部件。
2. **卡上必须有核验时间**（`research/01` §A1 的修正）。v2 §6.2 定的四项应扩成五项。核验时间是外部可核的、是差异点、是「我们真的进去看过」的唯一具体证据，把它放进折叠档案区是浪费。
3. **切面值必须有上下限双向准入**（`research/01` §B2 的修正）。v2 §4.4 只定了「至少命中 5 个站」的下限，漏了上限；Siteinspire 的 Typographic 命中 88% 等于没筛。本文用 12 条真实样本验证了双向规则的效果（§3.4）。
