## 1. 为什么现在需要一次不留情面的设计评审

VisLexicon 想解决的问题很真实，但已经被太多“正确的功能”包围了。

我们收集设计网站，做视觉词典，做组件索引，做图鉴，做设计分析工具，也想让人和 Agent 都能使用。每一项单独看都有道理，放在一起却越来越像一套复杂的数据库。为了让数据有秩序，我最近提出了 7 个大类、59 个小类、组合筛选、权重和一条分类进度轴。它很工整，也很容易写测试。

用户的反馈很直接：这套分组很差，没有真正的逻辑。页面上放几个按钮和下拉框，让人组合条件去找结果，看似条理清楚，实际上没有智能感，也没有真正理解用户为什么来。

这个批评成立。

底层的真实性、去重、证据和版权边界必须继续做严。前台的信息组织和发现方式则需要推倒一部分重新想。评审者的任务不是美化现有分类，而是判断 VisLexicon 应该怎样成为一个人愿意逛、愿意学、也愿意交给 Agent 使用的产品。

## 2. 产品到底想做什么

VisLexicon 不是一个单纯的网站导航，也不是另一个组件库，更不是只讲术语的 Wiki。

它面对两类使用者。

第一类是人。这个人可能是设计师、前端工程师、产品经理、学生，也可能根本不会写代码。他脑子里经常只有模糊需求：

- “我想做一个 Agent 的聊天界面，有没有成熟组件？”
- “我看到一种效果，但不知道它叫什么。”
- “我想找一套高级但不浮夸的图标。”
- “别人这个招聘官网为什么看起来这么像它自己的品牌？”
- “给我看一些真正做得好的三维网页，不要只给我一串链接。”
- “我想把这个网站的视觉语言提炼成提示词，让我的 Agent 参考。”

第二类是 Agent。它需要的不是一句“这个网站很高级”，而是稳定名称、定义、来源、截图、代码边界、许可证、参数、可引用地址和明确的验收标准。

因此，VisLexicon 的价值不应是“收得多”，而应是三件事：

1. 帮人把模糊感觉变成可继续行动的认识。
2. 帮人快速判断一个外部资源值不值得打开、能拿到什么。
3. 把人的选择变成 Agent 能继续使用的结构化上下文。

## 3. 用户已经反复讲清楚的要求

以下要求不是我的推断，而是多轮对话里反复出现的约束。

### 3.1 内容必须先做实

用户暂时不想继续堆表面装饰。他要先补齐内核。网站不能一边写着“收录 3000+、8000+”，一边只认真展示 6 个或 9 个，其余全部缩成没有图片、没有理解的一句话列表。

当前 8684 条记录只是从多个目录和搜索结果得到的候选。它们不是 8684 个已经理解的网站，也不是 8684 个独立产品。里面有重复 URL、同一产品的官网和仓库、同名不同产品、失效联盟链接、npm 包噪声，以及大量只靠原始目录标签生成的模板简介。

最新要求是：候选只是候选。只有真正进入官网、理解它在做什么、选出三个关键页面、写出人话简介并完成复核，才能公开展示。

### 3.2 所有公开网站要达到同一内容标准

不能再有“上面少量精品卡片，下面几千条低配目录”。

每个正式网站至少要有：

- 三张来自该站、互不重复、各自承担不同作用的截图。
- 一段不靠标签拼成的人话简介。
- 它究竟提供什么，适合谁，用户能拿走什么。
- 作者或组织、官方仓库、许可证和价格。找不到就明确写未知，不能猜。
- 来源页面与核验时间。

三张图不是随便三个 URL：

- 第一张说明“它是谁”。
- 第二张说明“它有多大、里面都有什么”。
- 第三张拿一个具体内容证明它真的能做什么。

### 3.3 每个网站都要真的进去看

批量脚本可以找候选页面、读取标题和准备截图，但不能替人判断。

之前的自动脚本曾经把 GitHub 的泛 AI 文章当成某个项目的代表页面，把纯白页当截图，把浏览器崩溃写成 2800 多个网站同时失效。这个教训很明确：自动化可以负责体力活，不能负责最后的编辑判断。

### 3.4 去重要贯穿全过程

搜索时要去重，进入候选池时要去重，Agent 领取任务前要去重，用户投稿时也要去重。

同一个产品可能同时出现为官网、文档、GitHub 仓库、npm 包、浏览器扩展商店页、旧域名和新域名。它们不能机械地算成多个网站。反过来，同名也不代表同一个产品，例如 Pika、Motion、Spectrum 都可能对应完全不同的东西。

未来用户提交一个 URL 时，系统应该先告诉他：

- 已经正式收录。
- 已在候选处理中。
- 这是某个条目的旧地址或仓库地址。
- 可能重复，需要确认。
- 看起来是一个新站点。

重复提交应该变成“给已有条目补证据”，而不是再建一条。

### 3.5 分类不能只是数据库分类

用户明确不满意我最近提出的 7 大类和 59 个小类，也不喜欢靠多组按钮、下拉框和标签组合来找结果。

这类做法的问题不是不够细，而是它把理解成本扔给了用户。用户先要理解我们的分类，再把自己的需求翻译成几个筛选条件，最后自己判断哪些组合可能有用。这更像后台管理系统，不像一个懂设计需求的产品。

### 3.6 过程要诚实可见

用户提过在左侧只放一条细竖轴，不做厚重侧栏。竖轴可以显示当前处理到哪个小范围、完成了多少。它的本意是让漫长的收录工作透明，而不是再造一套导航树。

这条竖轴究竟应该给普通访客看，还是只放在编辑/进度页面，需要评审者判断。把内部生产进度硬塞进普通用户首页，可能同样是工程视角压过用户视角。

## 4. 我们收录的对象并不是同一种东西

“设计网站”只是一个很粗的说法。下面这些站点的内容形态、用户目标和使用方式完全不同。分类设计必须先承认这些差异。

### 4.1 组件库、源码库和统一格式的可复用内容

这类站点的核心价值是“可以直接拿来用”。

#### 21st.dev

21st.dev 收录并托管大量社区组件、营销区块和主题。每个内容采用相对统一的展示方式，有实际预览、组件信息和安装入口。它不是简单给外部网站做导航，而是一个社区组件注册表和分发场所。用户进入它，通常是为了找现成界面并装进自己的项目。

#### shadcn/ui

shadcn/ui 提供可以复制进自己项目并继续修改的组件代码。它不是传统黑盒依赖。组件目录、文档和完整区块共同构成一套设计系统底座。用户得到的是代码、组合方式和长期可控性。

#### Magic UI、Coss UI、Hover.dev、Uiverse

- Magic UI 偏向营销官网、动效和高视觉冲击区块。
- Coss UI 偏向真实应用、后台和粒子级界面组件。
- Hover.dev 强在微交互、按钮、三维区块和动效页面片段。
- Uiverse 外观上像画廊，但每个社区元素附带 HTML/CSS 或其他实现，因此它本质上仍是可复用内容库，不是纯灵感网站。

#### Agent / AI 界面组件

这是一类越来越明确的小需求，包括聊天流、工具调用卡片、推理过程、来源引用、文件树、语音 Agent、审批、人机协作和生成内容预览。assistant-ui、AI Elements、Prompt Kit、LiveKit Agents UI 及大量新项目都属于这个方向。

这类内容可能来自完整组件站、单个仓库、某个大设计系统里的 AI 专区，甚至一个 npm 包。按“网站”分类会把它们拆散，但用户只关心“我现在要做 Agent 界面，哪些东西最有用”。

### 4.2 把外部网站整理成目录的导航站

#### Toools.design

Toools 自己不提供几千个组件。它把外部设计工具、素材站、学习资源、营销工具和灵感网站整理成目录，再把人导出去。它的价值在发现、筛选和覆盖面。

这类站与 21st.dev 不同：

- Toools 的主要内容是“其他网站”。
- 21st.dev 的主要内容是“站内统一展示和分发的组件”。

二者都可以叫“集合”，但用户拿到的东西完全不同。

类似形态还包括资源导航、工具目录、awesome list、组件库索引、字体导航和学习资源目录。未来应该明确区分“站内承载内容”与“只做外链导航”。

### 4.3 深度拆解品牌设计的参考库

#### Refero Styles

Refero Styles 不是普通网页截图画廊。它选取高级品牌和产品官网，用统一格式拆解它们的视觉方式，帮助人理解并参考。

首页的核心体验包括：

- 自然语言搜索。
- 一组会变化的风格词入口。
- Trending、Popular、Newest 三种浏览顺序。
- 三列卡片流。
- 海报加短视频的动态预览。

视频并不是全部同时播放。页面先显示海报，视频设置为静音、行内播放、初始不预加载。卡片进入视口才加载和播放，离开视口就暂停。页面会在视频结束后重新播放。实测片段长度并不统一，约 6.6 秒到 25 秒。

Refero 真正厉害的地方在详情页的信息节奏：

1. 先用一句容易记住的风格隐喻建立感觉。
2. 再用自然语言讲清克制、留白、颜色职责、排版和画面气质。
3. 继续展开颜色、字体、字号、字重、行高、间距、圆角、阴影、组件和布局。
4. 给出 Do / Don't，让人知道什么能学，什么会破坏这种风格。
5. 最后进入 Agent Prompt Guide 和多种导出格式，包括简版/长版 DESIGN.md、Tailwind、CSS 变量和 Design Tokens。

这是一条“先让普通人看懂，再让专业人钻深，最后让 Agent 拿走”的路径。我们应该学习这条路径，而不是复制它的页面样式或文案。

Refero 的不足也要看到：公开详情虽然提供原站地址和整体提取信息，但没有把每条颜色、布局或组件判断逐项连回具体页面、画面区域或页面证据。它的结果很完整，但用户很难判断某条规则到底是测量出来的，还是系统推断出来的。

版权边界同样明确：Refero 允许人把学到的洞察用于正常设计工作，但禁止批量抓取、再分发、建立竞争数据集、训练或评测模型。第三方截图、Logo 和商标仍属于各自权利人。VisLexicon 可以独立实现类似的信息节奏，不能搬 Refero 的视频、图片、文案、完整 DESIGN.md、界面代码或数据。

### 4.4 多案例灵感馆与流程图库

这类站点主要让人“看别人怎么做”。内容可能是截图、页面、用户流程、品牌案例或动效项目，但通常不能直接复制代码。

- Awwwards 收集并评选优秀网站。
- Mobbin 收集产品界面和用户流程。
- Land-book、Godly 等偏网页与落地页参考。
- SaaSFrame 偏 SaaS 页面、邮件和流程参考。
- Brands in Motion 收集品牌动效案例，并维护设计师与工作室目录。
- 60fps 等站点偏动效、交互和产品细节。

这类站和 Refero 也不同。普通灵感馆主要帮助“多看”。Refero 试图把观察进一步翻译成设计规则和 Agent 可读提示。

### 4.5 一个网站本身就是作品

有些网站不收录任何别的东西，也不提供组件。它本身就是值得看的对象。

例如 Kimi 的招聘网站可能用一整套独有的排版、文案、动效和品牌语气，让求职信息也成为一次审美体验。Linear 的产品官网、设计工作室官网、个人作品集、品牌活动页、实验性微站、时尚品牌官网也属于这一类。

它们的“可复用性”很低，但审美和表达价值可能很高。如果只按“能不能下载/复制”排序，它们永远在后面；如果用户此刻想做一个有鲜明品牌感的招聘页，它们反而可能最有用。

因此，给这种站统一贴上“商业展示，低权重”很粗暴。它忽略了用户目标。低权重只在“我要找可安装组件”这个任务下成立，在“我要找品牌表达参考”时并不成立。

### 4.6 真正用于完成工作的工具

Figma、Penpot、Spline、Framer、10Web、无代码建站器、UX 测试工具、配色工具、字体配对工具和 AI 设计工具都属于“进去做事”的网站。

它们和组件库的区别是：用户不一定拿走一段现成代码，而是在站内完成创建、编辑、生成、测试或协作。

它们和灵感站的区别是：页面再漂亮，用户的主要目标也不是欣赏这个网站，而是使用工具。

但同一个工具也可能提供模板库、案例库、教程和社区资源。它不应该被一个主分类锁死。

### 4.7 专业命名、模式、结构和学习库

这类站点解决的是“我不知道它叫什么，也不知道该怎样描述”。

- Component Gallery 研究不同设计系统里同类组件的命名、结构和差异。
- Laws of UX 整理设计与认知规律。
- UI Anatomy、Name That UI 帮人从界面位置和形态找到专业名称。
- animations.dev、Motion Vocabulary 等整理动效名称和模式。
- The A11Y Project 把无障碍要求拆成可执行清单和资源。
- Material Design、Apple HIG、ARIA Patterns 等提供规范和模式。

它们可能同时像词典、教程、规范、组件索引和参考库。用户来这里不是为了“下载资产”，而是为了理解和表达。

### 4.8 视觉素材库

图标、字体、插画、摄影、视频、音效、三维模型、纹理、样机和设计源文件都属于素材，但仍有不同使用方式。

- Lucide、Iconify 一类提供图标与代码接口。
- Fontshare 一类提供字体目录、字体详情、配对和逐字体许可。
- Unsplash 一类提供摄影素材。
- 还有插画库、Lottie 动效、音效库、3D 模型与材质站。

一个图标库可以同时是素材库、代码包、搜索工具和设计系统的一部分。把“图标”只当作某个树形分类节点，仍然可能不够。

### 4.9 社区、市场和注册表

社区和市场不是内容本质，而是内容如何产生、组织和分发。

Uiverse、21st.dev、Figma Community、模板市场、字体市场都可能让创作者提交内容。它们有作者、评分、收藏、许可证和安装方式。用户既可以逛，也可以直接拿走东西。

“社区”“市场”“注册表”更像站点运行方式，不一定适合与“组件”“字体”“教程”并列成同一层分类。

### 4.10 提示词、Agent 技能和机器可读设计资源

AI Skills for Design Engineers、Skills.sh、Agent 技能仓库、Cursor rules、提示词库、Design MD 样本和各种 Agent UI 资源，是传统设计导航很少认真处理的一类。

它们有时是代码，有时是文档，有时是工作流。用户要的不是视觉素材本身，而是让 Agent 更会做设计的上下文。

### 4.11 混合型网站才是常态

真实网站很少只属于一种类型：

- 21st.dev 是组件库、社区和注册表。
- Uiverse 是画廊、代码库和社区。
- Refero 是灵感库、深度分析器和提示词/设计文档出口。
- Component Gallery 是命名库、组件索引和学习资料。
- Figma 是工具、社区、素材市场和模板库。
- Spline 是工具，也有可复用案例和学习内容。
- Toools 是外部网站导航，本身也在影响用户如何理解设计资源的世界。

如果数据模型要求每个网站只能有一个“本质分类”，它会不断制造牵强判断。

## 5. 旧分类和最近 7 大类为什么不够好

### 5.1 早期分类来自采集来源，不来自用户需求

旧目录曾使用“视觉素材与字体、设计创作与原型、UX 研究与学习、UI 组件与设计系统、AI 设计工具、灵感与案例、协作与效率、品牌与营销、前端开发与动效”等大类。

这些名字看似熟悉，实际混合了内容、行业、工具、技术和用户动作。一个网站经常同时符合三四类。系统最后只能靠固定优先顺序选一个，于是 Figma、Linear 等会因为来自落地页目录而被错误归成“灵感”。

### 5.2 最近 7 大类仍然是“东西是什么”的树

我最近提出的 7 类是：

1. 可复用实现。
2. 可复用素材。
3. 专业知识与命名。
4. 可操作工具。
5. 资源聚合与导航。
6. 灵感与案例。
7. 单站展示与商业官网。

它比旧分类清楚一些，也有利于数据检查，但仍有几个根本问题。

#### 第一，它假定每个站点有唯一主身份

21st、Uiverse、Refero、Figma 等都会被强行压成一个答案。数据看起来整齐，真实理解反而变薄。

#### 第二，它按资源形态分，不按用户任务分

用户说“我要做 Agent 的界面”时，最好的答案可能同时包含：可安装组件、交互模式解释、优秀产品案例、图标、语音动效和一个分析工具。让他先去七个分类里逐个找是不合理的。

#### 第三，所谓固定权重没有上下文

组件库对“马上开发”很重要，对“找招聘官网的品牌气质”未必重要。Kimi 招聘站对前一个任务权重低，对后一个任务权重高。一个全局分数会把上下文差异抹掉。

#### 第四，59 个小类会迅速变成编辑部内部语言

小类越完整，用户越需要先学会我们的体系。最后页面只能加更多下拉框、更多按钮和更多标签，智能感越来越少。

### 5.3 分类可以保留在后台，但不一定该成为前台导航

底层仍需要字段来去重、做质量检查、统计覆盖和训练推荐。问题是：这些字段是否应该直接暴露为首页上的大类、复选框和下拉框？

更可能的答案是：不应该。

评审者需要重新判断：哪些分类属于编辑部内部结构，哪些属于普通用户看得懂的入口，哪些应该由系统根据一句自然语言自动组合。

## 6. 当前网站长什么样

当前前台还没有完成最新重构。真实页面大致是下面这样：

┌────────────────────────────────────────────────────────────┐

视觉上，策展页参考 Oreo Design：温润浅灰画布、白色大圆角底板、三列紧凑卡片、80px 克制顶栏、380×330 卡片、很窄的列间距、画面右侧与底部淡出。这个方向目前基本成立，但它只是版式基础，不解决发现方式。

## 7. 目前点击一个网站后会发生什么

最新用户意图与早期 Claude 对话有过变化。

早期确定过“整张卡直接打开源站，不做中间详情”。后来用户明确提出：点击卡片后应先动画到一个浮在当前页面上的小窗，让人看到作者、GitHub、三张关键图和更细致的人话说明，再决定是否访问源站。最新要求应优先。

当前浮窗已经有基础形态，但内容仍偏数据库：

- 站点名称和域名。
- 三张图。
- 一段简介。
- 作者、源码、定价。
- 标签。
- 访问源站按钮。

更合理的详情也许应该直接回答：

- 这个网站究竟是什么？
- 你能从这里拿到什么？
- 最值得先看的三个位置是什么？
- 它适合什么任务？
- 哪些东西能复制、安装或下载？
- 许可证有什么限制？
- 为什么系统把它推荐给当前用户？
- 能否把它加入对比、加入设计板，或提炼成提示词？

标签可以辅助理解，但不应该成为详情的主体。

## 8. 我原本准备怎样重做策展页

下面是当前方案，不是不可推翻的结论。

### 8.1 值得保留的底层规则

这些内容主要解决真实性，不是前台分类：

- 候选和正式公开严格分开。
- 每个正式站都由 Agent 真实探索。
- 三张图分别说明身份、范围和具体证明。
- 简介不能用分类标签拼接。
- 官网、仓库、旧域名和商店页按真实产品去重。
- 所有图片保存尺寸、哈希、字节数和来源。
- 一名 Agent 整理，另一名 Agent 复核。
- 发布采用版本文件，避免旧缓存和半写入。
- 用户投稿先查重，重复时补证据。

这套底层目前已经有相当多实现和测试。它应该继续保留，即使前台信息架构完全推翻。

### 8.2 原计划中的前台方案

原计划是把上方精选区和下方目录合并成一个统一页面：

- 所有正式站使用同一张三图卡。
- 只有核验完成的站点出现。
- 默认按一个全局价值分排序。
- 顶部按 7 大类和小类筛选。
- 左侧一条竖轴显示当前正在处理哪个小类。
- 点击后打开统一详情浮窗。

用户已经指出：这种结构太像整理得很好的资源数据库，仍然不够聪明。7 大类、59 小类和多条件筛选都需要重新设计。

## 9. 一个可能更接近用户心智的方向

这部分是供评审者批判的设计假设。

### 9.1 不再让分类成为首页的第一句话

首页第一入口可以是一句自然语言输入：

> 你现在想做什么，或者你看到了什么？

用户可以：

- 描述任务，例如“我要做一个带工具调用和审批的 Agent 界面”。
- 描述感觉，例如“像瑞士海报，但不要太冷”。
- 输入一个不知道名字的效果。
- 粘贴网站 URL，让系统分析。
- 放一张截图，让系统找名称、类似案例和可用资源。

系统不要求用户先选类别。它理解需求后，组合不同形态的结果。

### 9.2 一次回答可以混合不同资源，但要解释为什么

例如用户输入“我要做 Agent 界面”，结果不必是一串“Agent UI 组件”：

```text
可以直接用
  assistant-ui / AI Elements / Prompt Kit / LiveKit Agents UI

先看懂常见结构
  消息流、工具调用、推理过程、来源引用、人类审批等图鉴词条

看看优秀产品怎么处理
  Kimi、Claude、ChatGPT、Cursor、Linear 等真实界面与品牌案例

补齐视觉细节
  图标、空状态、加载动效、语音波形、代码块和文件树资源

把需求交给 Agent
  自动生成一份带来源和验收标准的设计说明
```

这里仍然有组织，但组织来自当前任务，不是固定分类树。

每个结果应显示一句“为什么出现在这里”，例如“包含可直接安装的工具调用卡片”“适合看推理过程如何折叠”“这是品牌参考，不提供源码”。这比一堆标签更像系统真的理解了需求。

### 9.3 分类变成后台的多维画像

网站不必只有一个主类。后台可以记录几个互相独立的问题：

- 用户能拿到什么：代码、素材、知识、工具、案例、提示词。
- 内容如何组织：站内统一内容、外部链接导航、单个品牌官网、社区市场、深度分析。
- 用户主要做什么：复制、安装、下载、学习、比较、创建、测试、欣赏、分析。
- 深度如何：快速扫一眼、完整目录、单项详情、可交互工具、系统拆解。
- 面向什么任务和媒介：网页、移动端、Agent 界面、品牌、动效、字体、三维、演示。
- 权利状态：允许复用、只允许外链、许可不明、禁止再分发。

系统根据当前问题动态选取这些维度。普通用户不需要看见全部字段。

### 9.4 首页不一定只有搜索

纯搜索会让不知道该搜什么的人无从下手。首页仍需要可逛的内容，但入口可以是“正在做的事”或“最近值得看的路径”，例如：

- 做一个 Agent 产品。
- 找一套图标语言。
- 学会识别常见界面结构。
- 看高级品牌官网怎样处理招聘页面。
- 为产品增加克制的动效。
- 从一个 URL 提炼设计语言。

这些路径不是永久分类。它们可以由编辑策划，也可以随内容与用户行为调整。

### 9.5 筛选不消失，但退到第二层

专业用户仍需要精确限制框架、许可证、价格、媒介和技术栈。它们可以放在搜索结果的“进一步缩小”区域，或由系统根据语句自动带上，不应该一进首页就面对五个下拉框。

评审者需要判断：怎样在“聪明的默认体验”和“专业用户的精确控制”之间取得平衡，而不是简单把筛选全部藏掉。

## 10. Refero 启发下的动态优秀参考

用户特别喜欢 Refero 卡片里几秒循环的视频。这个想法适合“优秀参考作品”，但不能机械地用于所有站点。

### 10.1 可能的卡片方式

- 卡片初始显示海报，避免同时加载大量视频。
- 卡片进入视口后才准备视频，真正可见时播放，离开视口暂停。
- 视频静音、行内播放，失败时回到海报。
- 用户减少动态效果时不自动播放。
- 移动端默认海报，只有网络允许且卡片成为主要焦点时播放。
- VisLexicon 自己制作的片段控制在约 5 到 8 秒，而不是照搬 Refero 的实际片长。

### 10.2 动态预览不能替代三张证据图

视频负责让人快速感受气质。三张图负责证明我们真的理解了这个网站。

动态预览应该是额外媒体，只在版权和许可明确时公开。不能把 Refero 或其他站点的视频下载回来重新展示。可以使用站方主动投稿授权、明确可再分发素材，或 VisLexicon 自有内容。

### 10.3 哪些内容适合动态预览

- 品牌官网和招聘官网的独特动效。
- 三维、滚动叙事和交互微站。
- 品牌动效案例。
- 组件库中的交互代表作。
- 词典里必须通过时间变化才能看懂的效果。

图标库、字体目录、普通文档站未必需要视频。统一内容质量不等于每种网站都用完全相同的媒体。

## 11. 网页 URL 转提示词与 Design MD 的工具

项目里已有一个参考仓库：`Paidax01/web-to-design-md`。它当前只有一个提交，没有许可证，因此只能研究思路，不能直接复制代码和模板。

它的基本方向是：让 Agent 用真实浏览器读取网页结构、计算样式、颜色、字体、间距、按钮、卡片和页面片段，再生成 DESIGN.md 与预览页。

值得吸收的原则：

- 先收证据，再写结论。
- 样式、页面结构和交互状态比单张截图更可靠。
- 多个页面先分别观察，确认视觉语言一致后再合并。
- 事实和推断应区分。

它目前仍像研究原型：

- 没有许可证、测试和稳定接口。
- 主要流程只保证桌面页面，移动端与交互态依赖 Agent 手动补充。
- 输出以 Markdown 为中心，字段与具体页面证据没有稳定对应。
- 预览页里部分格式入口只是展示，没有真正输出。

### 11.1 VisLexicon 可以做得更人性化

用户粘贴 URL 后，不应该立刻得到一篇长得像标准答案的设计文档。更好的流程可能是：

1. 系统展示它看了哪些页面、哪些区域。
2. 用白话概括“它给人的感觉”和最值得学的几点。
3. 每条判断标明是直接观察、系统推断还是用户修正。
4. 用户可以点“这条不对”“这只是偶然”“保留这个规则”。
5. 用户选择目标：网页、移动 App、演示、海报、图像生成，或具体 Agent/技术栈。
6. 系统再生成适合当前目标的提示词、简版/长版 DESIGN.md、设计变量或 JSON。
7. 每条关键规则可以回到来源页面和证据。

JSON 应该是事实源。提示词、Markdown、Tailwind 和 CSS 都是从事实源派生的不同视图。用户修改一条判断时，不需要整篇重新生成。

### 11.2 这项工具与策展的关系

- 在策展详情里，用户可以选择“分析这个网站”。
- 分析结果可以加入自己的设计板或生成 Agent 说明。
- 深度分析不能成为访问每个外部站的强制中间层。
- 对公开网站的分析要显示版权和可导出边界。
- 登录态页面优先本地临时分析，不默认上传敏感内容。

## 12. 词典和图鉴应该怎样存在

### 12.1 当前可靠内容

当前已有 62 个带本地可运行演示的正式词条。它们按布局、交互、美学、动效、组件等方向组织。

另外有 419 个有外部来源证据的 Visual Atlas 记录：

- 417 个仍是候选，只能展示定义和来源，不能伪装成本地完成的演示。
- 2 个与现有正式词条匹配，可以折叠到正式词条。
- 另有 194 个 AI Interaction Atlas 条目属于任务、动作、约束和渠道覆盖维度，不是视觉现象，不能计入图鉴数量。

后续曾尝试引入更多组件来源，把图鉴扩到 500+，但这条数据线还没有完整收口，不能把半成品数字当成果。

### 12.2 图鉴解决的不是“背词”

真实用户往往知道东西在页面的哪个位置、长什么样、起什么作用，却不知道名称。

因此词典首页不应该默认打开 Bento Grid，也不应该默认打开 Agent GUI。Agent GUI 只是一个场景，不代表整个视觉设计世界。

曾经确认过四种中立入口：

1. 我知道名称，或能描述它。
2. 我知道自己正在做什么。
3. 我知道它大概属于哪种现象。
4. 我想系统补全见识。

场景解剖图是一种发现方式。例如用户正在搭 Agent 界面，他知道输入区在底部，却不知道它叫 Prompt Composer。场景解剖可以帮他从位置找到名称。但它不应该占领默认首页。

### 12.3 网站策展和图鉴不应分成两个孤岛

一个经过分析的网站可以链接到图鉴词条：

- 某个招聘官网使用了什么排版、滚动、光标和过渡。
- 某个组件库覆盖了哪些常见结构。
- 某个 Refero 风格分析涉及哪些设计词汇。
- 用户从截图找到一个词条后，可以继续看到相关组件、工具和真实网站。

词典提供稳定语言，策展提供真实世界，工具把二者变成可交给 Agent 的设计说明。这三者应该互相解释，而不是只靠顶栏跳转。

## 13. 全站频道和目前关系

当前顶栏有四个频道：

- 策展：外部网站与设计资源发现。
- 词典：正式词条、图鉴候选和未来的场景解剖。
- 工具：颜色、差异、视觉测量、设计说明提取与未来 URL 分析。
- 提交：本地草稿和未来投稿查重。

这个分法暂时能工作，但评审者应判断：普通用户是否真的理解四个频道的关系？首页应该是策展，还是一个跨频道的智能入口？用户搜“Agent 界面”时，是否应该同时看到网站、词条、组件和工具，而不是先决定去哪一栏？

## 14. 哪些设计决定值得保留，哪些应该被质疑

### 14.1 值得保留

- 真实探索和三张关键图。
- 候选与正式内容分开。
- 去重、来源、许可和复核。
- 外部作者得到明确署名和流量。
- 不搬运无授权源码、高清图和 Refero 内容。
- 人话解释与 Agent 可读数据同时存在。
- 图鉴候选不伪造本地演示。
- 默认入口不被某一个场景绑架。

### 14.2 必须质疑

- 是否真的需要一个固定的 7 大类树。
- 是否应该让用户看见 59 个小类。
- 是否应该用一个全局分数给网站永久排序。
- 是否所有网站都必须用完全相同的卡片，而不是只保持同一内容质量。
- 左侧进度竖轴应不应该出现在普通用户首页。
- 顶栏四频道是否把本应统一的发现过程拆开了。
- 搜索结果是否应该按固定类别分组，还是按当前任务分成“直接用、先理解、看案例、用工具”。
- 页面是否太忠于 Oreo 的静态网格，压住了动态参考、场景发现和智能推荐。
- 浮窗详情是否只是把数据库字段换成漂亮排版。
- “智能感”究竟来自自然语言输入、推荐解释、上下文组合，还是另一个会聊天的外壳。

## 15. 请评审者完成的工作

请不要礼貌性肯定，也不要在现有 7 类上做小修小补。请从用户真正想完成的事情出发，给出一份可以推翻我方案的设计评审。

反馈文件至少回答下面的问题。

### 15.1 产品心智

- 用一句话重新定义 VisLexicon。
- 用户第一次进入时，应该立刻明白它能帮自己做什么？
- 人类用户与 Agent 用户是同一个产品的两种入口，还是两套体验？
- 策展、词典、工具、提交是否仍应作为顶层频道？

### 15.2 内容组织

- 固定分类树是否应该保留在前台？如果不保留，后台数据该怎样组织？
- 21st、Toools、Refero、Kimi 招聘官网、Figma、Component Gallery、Lucide 等混合形态应如何被理解，而不是硬塞进唯一主类？
- 请给出比“7 大类 + 59 小类”更符合用户需求的组织方式。
- 如果你认为仍需要分类，请明确分类依据，并用上述站点做压力测试。
- 如果你认为不该以分类为中心，请给出可操作的替代方案，不要只说“用 AI 推荐”。

### 15.3 首页和发现流程

- 首页第一屏应该是什么？
- 不知道搜什么的人怎样逛？
- 知道自己要做什么的人怎样直接拿到混合结果？
- 专业用户怎样获得精确控制，而不让普通用户先面对五个下拉框？
- 什么才是真正的智能感？请避免把聊天框当成唯一答案。
